# 4. Threat model

What Hearth defends, against whom, and where the defense stops today. Written to be read by someone deciding whether to trust Hearth with their children's photos. Status labels follow [README.md](README.md): **Built**, **Planned**, **Gap**.

## Assets

1. Photos of children, and their capture dates.
2. Who is in the family and how it is split (sides, households, who sees whom).
3. Words: titles, captions, comments, names.
4. Behavior: who opened what, when, from where.
5. Account identifiers: emails, push tokens, IP addresses.

## Adversaries and defenses

| Adversary | Goal | Defense | Status |
|---|---|---|---|
| **A relative outside a post's audience** | See a post, or learn it exists | RLS on every table; one visibility predicate (`private.sees_post`) behind RLS, the feed, `sign-media` and notices; not-allowed returns the same `404` as not-found | Built. By design, parents see every post in their family space |
| **A relative inside the family** | Learn whether another relative looks at posts | No last-seen, login or activity details shown (migration 0004); notices carry no viewing data | Built. Since Nov 19 (SEC-R2) the app no longer calls `mark_seen`, so no new view records are made; the server still lets an author read `seen_count` for old rows until a migration drops it (tracker R62, needs a deploy) |
| **A former member** | Keep access after removal | Access is checked at request time; download URLs expire in 10 minutes; photos kept for offline viewing (A3) are dropped at the next refresh that no longer lists the post | Built. A video being played is a short-lived decrypted file (`hearth-video/<media_id>.mp4`, deleted on Close, at sign-out and at the next start, signed in or not, PRIV-R1). **Gap:** photos already saved to their phone stay there; a decrypted video left by a crash stays until the app next starts; a phone kept offline still shows photos it had kept until it next refreshes |
| **Someone with a leaked link** | Download photos | Presigned URLs expire in 10 minutes and return ciphertext only | Built |
| **Someone with a forwarded or logged invite link** | Join the family as a relative | Invites are single-use, expire in at most 30 days and can be addressed to one email; the link token is 160 random bits and the typed code is rate limited (S10). Links point at the hosted web build, not at `hearth.family`, which isn't bought: whoever registered it would have received live tokens (migration 0014; `backend/scripts/smoke-check.sh` fails if hosted points there again) | Built. **Gap:** the token sits in the URL path, so the web host's request logs can hold it until it's used or expires; ONB-6 (milestone 2) moves it after `#`. Expo's EAS Hosting is the web host; where it keeps logs is not yet written down |
| **Storage vendor (B2) breach or insider** | Read photos | Phone-side AES-256-GCM; B2 never sees a key | Built |
| **Location stalker** | Find a child's home or school from a photo | EXIF and GPS stripped on the phone by a code-level media policy (location default `strip`), verified on the output bytes, enforced by a database check; videos cleaned on the phone the same way without re-encoding (`cleanVideo.ts`: location boxes, metadata tracks, dates and trailers removed, then verified); a video's poster frame is re-encoded through the photo thumbnail steps (cleaned and verified), or a bundled plain placeholder is used; video posting stays off (server `video_posting`, default off) until the iPhone check (FLAG-7) and Chase's word | Built (photos); built, not yet on (video) |
| **Ad, analytics or AI vendor** | Profile the family | None are present: no analytics, ad or crash SDKs; error reports are our own fixed-shape table, 30-day retention | Built |
| **Push and email providers** | Learn content | Notices carry display names, counts, the post kinds (`kind_counts`, migration 0034: "some news", "an event") and a link only; never the words, day, place, saying or a child's name or age | Built. **Planned:** names-off setting (D9) |
| **Account takeover** | Sign in as a relative | One-time email codes, 1-hour expiry; no passwords to reuse: migration 0028's trigger blanks `auth.users.encrypted_password` on every insert and update, so a password set through Auth's open `/signup` or `updateUser` never works (TS-SEC-R1), and "Confirm email" is on, so `/signup {email, password}` returns no session | Built. **Gap:** an inbox compromise is an account compromise. **Planned (DEC-57, off):** text codes through Twilio Verify. A text code is weaker than an email code: a SIM swap or number port hands the code to the attacker, and a relative can be talked into reading it out. Defenses planned: the text says never to read the code to anyone (BETA-SMS-17; needs a Twilio custom template), the guide never asks for it, phone and email accounts are separate so a swap doesn't reach an email account. Phone confirmations stay on, so no phone account exists without a texted code (PRIV-R1). Not defended: a completed SIM swap, or a carrier giving a relative's old number to someone new (number recycling) |
| **SMS pumping (toll fraud)** | Run up Hearth's text bill by requesting codes to premium or foreign numbers | **Planned, off:** US-only numbers in the app (BETA-SMS-3); Twilio Verify Geo Permissions US only and Fraud Guard; Supabase `max_frequency` 60 s per number and the project-wide `sms_sent` hourly cap; small prepaid Twilio balance with auto-recharge off as a hard spending cap (`docs/eng/SMS-PROVIDER.md`) | Planned |
| **Hearth's operator, or whoever compromises Hearth's server** | Read everything | Least-privilege grants, keys only in function secrets, no keys or captions in logs | **Gap:** the server can unwrap every photo key and read all captions and comments. Fixed only by the family vault |
| **Anyone who reads Hearth's database or function logs** (operator, breach, legal demand) | Learn where relatives are, or match accounts to addresses | Hearth's own tables keep no IP address: the invite rate limit (S10) stores a keyed HMAC of the address, cleared daily, and the key (pepper) is replaced daily so a dump or backup can't reverse older hashes (migration 0012, `backend/tests/privacy_audit_test.sql`). No `console.*` call in the app or the edge functions logs a key, URL, caption, email or raw error; CI enforces it (`scripts/check-logs.mjs`) | Built. **Gap:** Supabase's own logs sit outside our code and can hold IP addresses. On the Free plan Supabase lists 1 day of API and database log retention and 1 hour of Auth audit logs (supabase.com/pricing and docs/guides/auth/audit-logs, checked Oct 18, 2026); paid plans keep them longer. Supabase Auth can also write its audit log, with an IP address field, into `auth.audit_log_entries` in our own database; `backend/scripts/smoke-check.sh` counts those rows (never printing them) and warns. Supabase backups and point-in-time restore keep database rows (including hashed rate-limit keys) for their own retention window, not yet written down |
| **Legal demand to Hearth or Supabase** | Obtain family data | Data minimization; US storage | **Gap:** what's readable by the server can be produced. Supabase contracts through a Singapore entity |

## Out of scope (today)

- A compromised phone (malware, an unlocked device in someone else's hands).
- Screenshots or saved copies made by a legitimate viewer.
- Traffic analysis by network observers (timing and sizes of encrypted transfers).
- Denial of service.

## Known gaps, in priority order

1. Server-held keys and plaintext captions and comments (03 roadmap; family vault).
2. One `MEDIA_KEK` for all families; no rotation procedure (D8).
3. Hard purge not scheduled on the hosted project; B2 deletion, auth-user removal and export worker not written (02 "Deletion").
4. Residency: Supabase logs outside the US; push via Apple and Google (01 "Residency").
5. No outside security review yet; open-sourcing is undecided (D10).
6. Open starting (migration 0024, DEC-55): any signed-in account can start one family of its own with `start_family`. Joining another family still needs an invite. The switch `start_family_open` ships off; with it on, strangers can store photos on Hearth's bucket. Defenses: one family per account, 3 starts a day, a photo and storage cap on app-started families (`HF001`), and the direct `create_household`/`create_space` calls revoked from app users. Now built, still off (START-ON-1..4, PRIV-R7): Help shows everyone a "Something wrong?" section with an Email Hearth button when the build has a help email (`EXPO_PUBLIC_HEARTH_HELP_EMAIL`, kept out of the repo), and the start button is hidden when it doesn't, so nobody starts a family with no way to reach Hearth; the mail carries only a fixed subject, no family, group or person. Chase can suspend a reported family with `backend/scripts/suspend-family.sh` (sets `spaces.deleted_at`: every member gets not found and uploads are refused; `--undo` brings it back; `purge_soft_deleted` can remove it after 30 days but isn't scheduled yet, gap 3), lift a known family's cap with `--known`, and flip the switch with `start-family-switch.sh`, all through the Management API with a dry run by default; a bad account is banned in the Supabase dashboard ([RUNBOOK-START-FAMILY.md](../eng/RUNBOOK-START-FAMILY.md)). Not yet: an age and legal review (PRIV-R5, milestone 7), a cold test with a parent who isn't Chase (BETA-START-9), and Chase's word to turn it on.
7. Life calendar (migration 0029): a member's birthday shows under their name to everyone who may see that name, and a date with no member to the family's Everyone group (PRIV-R2). Labels are free text a parent types; they never go into logs, errors, reports or notices, but they are stored in plain text like captions (gap 1). The rule that dates follow who sees a name is pending Chase's confirmation (DEC-81).
8. Messenger: no key verification (a compromised server could add a hidden phone to a chat), and chat metadata is visible to the server ([06-messenger.md](06-messenger.md)).
